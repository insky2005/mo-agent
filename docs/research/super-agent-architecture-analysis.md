## 0. 结论摘要

文章描述的 Super-agent，本质是**把操作系统的调度结构搬进 Agent 系统**：常驻 Router 当内核，上下文隔离的 Worker 当进程，Trigger 当中断，Thread 当 fd 就绪表，上下文窗口当物理内存，Watchdog 当硬件看门狗。它的每一项设计都能在计算机系统里找到同构物（见 §3）。

对 mo-agent 的判定，分三层：

| 问题 | 回答 |
|---|---|
| 现在的 mo-agent 是 Super-agent 吗？ | **不是，而且是反向定位。** mo 的 ADR-0001 承诺"观察优先、不托管 Agent"，它做的是**人盯不过来时的那一层**（把人上移），Super-agent 做的是**把人从执行里摘出去的那一层**（把 Agent 上移）。两者在"人的角色"上相反。 |
| mo-agent 有能力做到类似的事吗？ | **底座够，中枢缺。** Super-agent 最难自建的三样周边，mo 都已经有了（§5.2-1/2、§5.2-5、§5.2-7/8）——只是都停在「单次任务」这个粒度上，没有一个是「持续会话」的。**缺的是那个"有模型、不干活、常驻"的 Router**，以及它必须配的三件套：Trigger 语义过滤、Thread 订阅、上下文引用图。 |
| 该不该去做？ | **不该做 Router，该做 Router 之上缺的那一层。** 文章 §8.4 自己承认"安全与隐私没解决，Super-agent 只能在小范围可信环境里工作"。而 mo 的全部工程积累恰好是"不自动放行、批准留人、指纹校验、超时交回、改动可回退"。**在 Super-agent 里 Router 会变成 commodity，信任不会。** |

**一句话**：mo 现在缺的不是能力，是定位。要么寄生一个别人的 Router（战术，§7.2 路径 B），要么把自己做成所有 Router 都要倚赖的治理与度量层（战略，§7.2 路径 C）。

## 1. 文章在解决什么

问题链条很干净，值得复述，因为**每一环都决定了下一环的架构选择**：

1. 单任务 Agent 已证明"模型会用工具解决复杂问题"，人的干预在减少；
2. 人的角色因此上移到"决策与验收"，于是出现了持续在线的个人助手形态；
3. 但主流 Agent 仍以**单一 Session** 为基本单位，Session 之间彼此独立；
4. 于是**多任务的上限不是模型能力，是人的注意力**——实测一个人只能同时跟进 3–5 个活跃 Session；
5. 在单会话上做 CLI/MCP/连接器式的扩展，解决不了三件事：同步阻塞、多任务上下文混乱、本地设备离线即停。

要突破，就得让 Agent 不再是"一次手动会话的附属物"，而是一个**跨会话保持上下文、并行推进多任务且互不干扰的连续实体**。

**我的补充判断**：这四条其实不是四个产品特性，而是**一个系统属性被拆成了四个视角**。真正被解决的是"Agent 从函数调用模型变成常驻服务模型"——从"请求-响应"变成"事件循环 + 调度 + 状态持久化"。所以它必然要用操作系统的老办法，这不是类比修辞，是约束推导出的唯一解。

## 2. 五个模块的机制拆解

### 2.1 双层架构 [2] → 连续 + 高效

要解决的根本权衡：**连续性与吞吐量不可兼得**。

| 做法 | 连续性 | 吞吐 | 问题 |
|---|---|---|---|
| 所有事件进同一个 Session | 最好 | 最差（单 ReAct Loop 串行） | 中间细节混杂，多任务互相污染 |
| 每条事件新开 Session | 最差 | 最好 | 无全局上下文，多 Session 各自回话导致交互混乱 |

解法是把"维护全局连续性"和"高并发执行"拆到两层：

**Router 层**
- 常驻，承接所有人类入口，是所有跨任务信息与决策的汇总点——全局序点、协调点、记忆；
- **不直接执行任务，甚至可以不配 Bash**。这是关键：一个全局节点一旦开始干重活，就成了吞吐瓶颈和故障单点。用操作系统的说法：内核不做用户态工作。
- 与常见 Agent Team 的区别：Team Lead 要深入拆解子任务、高频协调，自身推理负载很重；Router 只处理**任务之间**的高层关联与分派，不介入单任务内部。因此 Router 可以用轻量模型。
- 为什么单个 Router 会话没成为瓶颈：**上一轮推理期间到达的 Trigger 会积压，下一轮合并注入**。Router 每步是"长输入、短输出"，合并后 Prefill 阶段并行计算，单次请求耗时的增长远慢于 batch 增长。作者给了实测：batch 1.0→2.8，单次 2.5s→3.9s，**分摊到单个决定的时间反而从 6.4s 降到 1.6s**。拥堵时反而更划算。
- 扩展路径：多层过滤，或水平分片（但分片会牺牲全局记忆连续性）。

**Worker 层**
- 上下文隔离，挂完整执行工具，独立上下文里专注一个任务；
- 用最强的模型（它决定交付质量）；
- **不与人类直接交互**：推理与工具调用不外泄到信道，只向 Router 汇报状态，由 Router 统一回话。这一条同时解决了"并发度"和"多会话抢话"两个问题；
- Worker 之间通常不直接通信。冲突发生在同一个 PR 等共享环境时，靠**共同订阅同一个 Thread** 自然发现并自行解决；少数跨任务协同由 Router 中转；
- Worker 内部可以再套 Subagent 或 Agent Team，对 Router 透明。

**本文最重要的一条工程结论**（在 §7.1 实验里被数据证明）：分工**不能交给模型的临场判断**。

实验里"单 Session + Subagent 工具 + 中性提示"5 次运行**一次都没调用 Subagent**，所有工作都在主会话里做并被新消息不断打断，p95 达 29.5 分钟；改成"提示优先委派"后 4/5 次开始委派，但仍有 1 次模型自己判断"这事很小"而亲自做了，形成长尾。而双层架构 p50 12.4 / p95 15.7 分钟。**把"要不要分工"写在提示词里，是把系统结构问题降级成概率问题。**

### 2.2 事件驱动 [3] → 主动

驱动源从"人逐条敲的提示词"换成"环境里的半结构化事件"（Trigger）。四个递进问题：

**① 事件过滤（Fast Path / Slow Path）**
真实事件流是"高噪音、低触发率"。每个事件都调模型判断，延迟和成本都不可接受。
- 程序层（Fast Path）：按来源、群组范围、用户/机器人白名单做确定性准入，把明确的高频判断固化成代码；
- 语义层（Slow Path）：通过准入的候选才交给 LLM 按提示词策略判断；
- 附带价值：语义层就是**面向人类的自然语言扩展点**——加策略不用改代码。

**② 事件路由（订阅与直通）**——同样是 Fast/Slow Path
- 同一个 PR、同一个 IM 话题、同一封邮件串下的连续事件构成一条 **Thread**；
- Router 用 Thread 的初始事件创建 Worker 后，Worker **直接订阅该 Thread**；
- 此后同一 Thread 的事件由程序**直通**给订阅者，不再经 Router（Fast Path）；Router 只处理**尚未被订阅的新事件**（Slow Path），但仍可观测全部事件以掌握全局状态；
- Thread 与 Worker 是**多对多**：一个 Worker 可订阅多个 Thread，一个 Thread 可被多个 Worker 订阅——这就是 Worker 之间"不点对点通信也能发现冲突"的机制；
- Worker 的输出侧仍统一汇报给 Router。

**③ 上下文组织（Inline & Spill + 链式召回）**
> "浪费上下文窗口，就是浪费模型的智能。"

把上下文窗口当 **Cache** 管理：
- **Inline**：近期很可能用到的信息直接内联，省掉工具调用往返。从最小信息起步（ID + 摘要），再按**局部性**逐步加：先关联对象 ID，再时空相邻内容（前 50 字、IM 前后相邻消息、被回复的消息、评审讨论里的相邻评论）；
- **Spill**：超出预算或低频的完整内容留在窗口外，窗口里只留引用/摘要。最简做法是截断 + 保留续读入口；
- **链式召回（Chain of Recall）**：给 Trigger / Thread / Worker Session 赋唯一 ID，注入时内联**下一跳的 ID**，于是这些对象在底层构成一张引用图。因为召回结果本身也遵循 Inline & Spill，模型可以沿着引用关系逐跳按需展开——从一条消息 → 所在 Thread → 关联 Worker → 该 Worker 的另一个评审 Thread。这缓解了 Router 在长程中丢失上下文的问题，**而不需要把全量历史塞进窗口**。

**④ 投机执行（Speculative Execution）**
在结果是否被采用还不确定时，先用后台算力试：有价值就交付，没价值就丢弃。个人助手场景是"收到会议邀约就先查冲突、备资料、起草回复"；研发场景是"静默复现并修复"——群里有人反馈问题时后台先尝试复现和修复，**只有确认问题且找到简单修复才交付，否则全程安静**。

### 2.3 面向人的交互 [4] → 连续 + 高效

**① 异步 ReAct Loop（半双工 → 全双工）**
经典 ReAct 的 `run()` 是同步阻塞的：工具跑多久，会话就哑多久。改成 `start()` / `stop()`：调用后立即返回 Started，循环不再等待；后台完成后把结果**作为一条新事件**投递进会话；模型也可主动 `stop()` 掉跑太久的后台命令。
（文中明确：这一机制**已在 DeepSeek Harness 实现，但尚未默认开启**。）

**② 多信道交互（带宽匹配）**
- 任务内部的冗长推理与密集工具调用已被双层架构隔离在 Worker 内，不外泄；
- IM 等即时信道：低打扰、只问直接问题、给简短结论，**单次回复 ≤ 100 词**；
- GitHub / 邮件 / 文档等异步信道：结构化、高信息密度（完整背景、改动说明、验证结果）。

### 2.4 计算、状态、环境分离 [5] → 持久

现有本地 Agent 把三件事绑在同一台设备上：推进循环的计算、需持久保存的会话状态、执行环境（仓库与工具链）。设备一休眠，Agent 就死。

两步解耦：
1. **计算 ↔ 状态**：Agent Loop 做成**无状态**、放进云端弹性容器；Session 状态进数据库。容器可重启可替换，连续性由存储保障。
2. **计算 ↔ 执行环境**：**不把环境搬上云**。真实环境里有未提交改动、私有凭据、内网依赖、特定硬件，复制成本高且容易漏；要求用户迁到云端则迁移成本太高。所以让 **Agent Loop 在云上，环境留在原地**，端侧只装一个**不保存会话状态的轻量 daemon**，只负责执行命令、返回结果。
   - 与 Anthropic "脑手分离"一致（harness 无状态、会话日志在 harness 之外、统一接口接环境）；
   - 差异在场景：那篇讲托管服务与按需沙箱/VPC；这里首先要接的是**用户日常使用、可能间歇在线的个人机器**；
   - 于是支持 **BYOM（Bring Your Own Machine）**、托管机、按需环境；甚至能在用户的某台设备重新上线后，由云端 Agent 自动触发完成必须在该设备上跑的任务。

### 2.5 Watchdog [6] → 持久（自愈）

长期运行的分布式系统很难只靠主系统内部逻辑保证可靠，需要系统外的 **Control Loop**。而且：
> 在 Agent 系统里，仅靠进程存活探测或监控脚本是不够的，因为许多异常不是进程崩溃，而是**模型陷入无效循环或偏离目标**。

所以外部独立一个 **Watchdog Session**，用定时消息驱动：
- 处理基础设施故障（接口报错、状态恢复失败）；
- **由模型判断每个 Worker 是否有实质进展、方向是否偏离整体目标**；
- 发现异常及时介入，偶发外部故障则持续复查；
- 因为 Watchdog 自己也是带完整工具的 Agent Session，维护者可以用自然语言问它故障原因，也可以让它在线改主系统行为（增删提示词、调触发规则）。

## 3. 另一种读法：这套架构其实是把 OS 搬进 Agent

文章自己说"许多问题与传统计算机系统长期探讨的问题高度相似"。把这张映射表列全，它的预测力比逐条复述强得多——**凡是表里右边还空着的位置，都是这套架构迟早要补的洞**。

| 计算机系统 | Super-agent | 为什么是同一个问题 |
|---|---|---|
| 内核 / 调度器 | Router 层 | 只决定"下一步谁跑什么"，不执行业务；不配 Bash = 内核不做用户态工作 |
| 进程 / 地址空间 | Worker Session | 上下文隔离是**并发正确性的前提**，不是性能优化 |
| 隔离进程 vs 共享内存 | 上下文隔离 vs 全局记忆 | 同一权衡：隔离换吞吐，共享换连续 |
| 中断 + 就绪队列（epoll） | Trigger + Thread 订阅 | 事件驱动、多对多注册、边缘触发 |
| 中断合并（interrupt coalescing） | Router 的 Trigger batching | 固定成本摊薄：批越大，单次越便宜 |
| 系统调用 fast path / slow path | 程序策略 / 语义策略 | 高频确定判断下沉为代码，只有需要"理解"的上行给模型 |
| 页表 + 缺页中断 + 按需换入 | Inline & Spill | 窗口 = 物理内存，只装热页，冷页留引用 |
| 指针 / 多级页表遍历 | 链式召回 | 用 ID 串联，逐跳展开，不预先全量加载 |
| 分支预测 / 投机执行 | 静默复现并修复 | 赌赢省延迟，赌输丢弃，成本是后台算力 |
| 阻塞 syscall → 异步 I/O（io_uring） | `run()` → `start()` / `stop()` | 等待不再阻塞调用方，完成事件回投 |
| 硬件看门狗 / 外部复位电路 | Watchdog Session | 主系统无法自证可靠时，必须有系统外的复位能力 |
| 存算分离 / 无状态计算 | Loop 进容器、状态进 DB | 计算可替换，状态不可丢 |
| 设备驱动 / 块设备 | 端侧 daemon | 真实状态留在原地，按需读写 |

**推论一**：如果"模型能力继续上涨"这一前提成立，那么**表里所有纯调度类位置（Router、过滤、召回、批处理）都会稳定地被更小更快的模型吃掉**——这正是文章 §8.1 提出 Router 专项训练（co-design）的依据。

**推论二**：但**"信任、审计、权限、人的最终裁决"这类位置不会被模型能力替代**。它们不是智能问题，是治理问题。这直接指向 mo 的位置（§7.2 路径 C）。

**推论三**：这套架构的隐含假设是"模型是 CPU"——能力足够，瓶颈在系统。所以**架构投资的回报率随模型能力上升而上升**，不会因为模型变强而过时。反过来，任何"用提示词解决系统问题"的做法，都会被模型变强所稀释（§2.1 的实验已经证明了）。

## 4. 实验怎么读，以及不能推出什么

### 4.1 消融实验（§7.1）

设置：约 300 条消息，其中约 20 条是工作请求，其余是闲聊/跟进/叫停/CI；编码工作用**只消耗时间的工具**替代；每方案重复 5 次。

| 方案 | p50 | p95 | 备注 |
|---|---|---|---|
| Super-agent（完整） | 12.4 min | 15.7 min | 读缓存 token 更高 |
| Super-agent 去掉直通 | ≈ 同 | ≈ 同 | **Router 决策 +30%，token 2323 万 → 3177 万（+37%）** |
| 单 Session + Subagent（中性提示） | — | 29.5 min | 5/5 次**一次都没委派** |
| 单 Session + Subagent（优先委派提示） | — | 介于两者 | 4/5 次委派，1 次自判"很小"自己干 → 长尾 |

**能推出的**：
1. 分工必须结构化，不能靠提示词（最强的结论）；
2. 直通机制的价值是**成本**，不是速度或质量——质量不变而 Router 决策 -30%、token -37%。所以快慢路径要按"成本/质量"两个轴分别评估，别混在一起说"更快"；
3. 双层架构用**更多 token** 换**更短且更稳**的完成时间，是明确的花钱买确定性。

**不能推出的**：
- 工具是"只消耗时间"的假执行者，因此衡量的是**调度与协作能力，不是交付质量**。不能据此断言真实编码任务的 p95 也会同样改善（真实任务里 Worker 自己也会卡住、需要人介入）。
- 合成负载只有 20 条工作请求，直通收益随 Thread 密度强烈变化；真实团队密度不同，37% 这个数字不可外推。
- 5 次重复下的 p95 置信区间必然很宽，只应作趋势看。

### 4.2 Router 批处理（§7.2）

Trigger 到达速率 1 → 40 条/分钟：平均 batch 1.0 → 2.8，单次请求 2.5s → 3.9s，**单个决定分摊 6.4s → 1.6s**。

这是 prefill 的规模经济学：合并进一次调用，prefill 阶段并行计算，单次耗时的增长远慢于 batch 增长。**但它的成立前提很窄**：
- Router 每步是长输入短输出（输出 token 才是串行的）；
- 上下文没爆；
- 模型单轮能准确处理这么多条 Trigger（文章自己列为上限）。

真实系统里这个甜点区会随 Trigger 复杂度上移而收窄——**一旦某些 Trigger 需要 Router 更长的思考，批处理就从收益变成"一次判断错一批"的风险放大器**。这是文章没展开但必须预判的失效模式。

## 5. mo-agent 现状盘点（按代码事实）

### 5.1 一句话定位

> **mo 是一个只读的观测面 + 一个会写文件但不调模型的派单台。**

**决定性事实**：在 `core/` `host/` `cli/` `adapters/` `approvals/` 里 grep 不到任何模型 provider（anthropic / openai / chat-completions / apiKey 全无）。全仓唯一运行的模型是**本地 whisper.cpp 做 ASR**（`host/voice/whisper.mjs`，不上传）。mo 的所有"判断"都是规则表与状态机。**这不是缺陷，是 ADR-0001 的直接后果**——观察优先意味着不掌控推理，智力全部留在外部 Agent 里。

同时要看清空间关系：文章描述的 Router/Worker 是**在 DeepSeek Harness 里实现**的；mo 是同一台机器上**与它并列的另一个平面**（观测 + 决策 + 派单）。所以这不是"mo 落后于 DSH"，而是"两个平面各管一段"。

### 5.4 对现有设计的三条复核意见

对照文章的实验结论，mo 现在有三处**同构的失效模式**：

1. **用文案约束系统行为**。`core/manager/contract.mjs` 的 `RULES` 里写"一次对话最多派 3 个任务""没确认不派单""不要自己写回执"，`FORBIDDEN` 靠"不暴露工具"来保证。这与文章 §7.1 里"用提示词要求模型分工"是同一个失效模式：**约束越靠文案，越依赖模型的临场遵守**。实验已经证明这种约束在 5 次里会漏 1 次。可行的加固方向：把限制变成**可计算的不变量**（配额计数在 core，派单时校验），而不是一句话。
2. **回执是文件 + 轮询，属同步阻塞范式**。派单→等回执→`ingest`，本质是 `run()`，不是 `start()`。文章 §4.1 的结论是把它改成事件投递。mo 已经有事件总线，却让任务结果走文件系统，等于在事件架构里留了一条阻塞支路。
3. **看门狗要靠外部 cron 才会跑**。`cli/watchdog.mjs` 的注释是"给 cron / launchd 用的一次性清扫"，而 host 里没有任何定时驱动它。所以"持久"这一项目前是**名义上的**。

## 7. 判定：能不能做到类似的事情

### 7.1 三层回答

**第一层：作为产品主张，不能，而且是刻意的。**
ADR-0001 把"不托管 Agent、不改变运行方式"写成了架构承诺，[architecture.md](../architecture.md) 的依赖方向、`adapters` 的"只陈述事实，不决定通知文案"、`approvals` 的"不直接推送"，全都是这条承诺的展开。要变成 Super-agent，**必须改 ADR**，不是加功能。所以这个问题的答案不是技术性的，是治理性的。

**第二层：作为能力底座，能，而且底座比想象中完整。**
文章里最难的三件事——(a) 把多家异构 Agent 的原始信号归一成一套事件词汇表；(b) 接真实工作信道并让人在任意信道做决定；(c) 把"派单 → 执行 → 验收 → 归账"做成机器事实——mo 都做了，且有测试保护（585 项）。这三件事恰好是"自己写一个 Router 容易、把周边接齐很难"里的那个"周边"。

**第三层：缺的是中枢，且中枢是三件套。**
一个常驻 Router 本身不难（就是一个不配工具的 DSH 会话）。难的是让它成立的三件配套：
1. **Trigger 语义过滤**——没有它，Router 会被噪音淹掉；
2. **Thread 订阅与直通**——没有它，Router 会被自己的转发量压垮（文章实测省 30% 决策 / 37% token）；
3. **上下文引用图**——没有它，Router 跑一周就丢全局。

这三件**都不需要模型能力**，都是数据结构与路由表。**它们才是真正的工程量。**

### 7.2 三条路径

**路径 A：自建（在 mo 里长出 Router + Worker 编排）**
需要引入模型客户端、ReAct 运行时、工具层、会话隔离、异步工具、上下文管理——即 DSH 已经有的全部东西。
- 成本：高（等于重写一个 harness）
- 收益：完全自主
- 风险：违背"不绑厂商"，且 mo 的核心价值（跨 Agent 中立）会被稀释
- **结论：不推荐**

**路径 B：寄生式双层（战术/验证）**
Router = 一个常驻的 DSH 会话（用现成的 `dsh.createSession` + `dsh.prompt`）；Worker = mo 的 dispatch 或 DSH 子会话；事件面复用 `hub`；上下文注入复用 manager kit（MCP）+ `knowledge/recall`；Watchdog 复用 `cli/watchdog` + 一个模型化的"进展判断"。
- 需要新写：`RouterAdapter`、`core/thread.mjs`（订阅表）、batch 注入、动作三选一（派单 / 回话 / 忽略）
- 成本：中
- 风险：深度耦合 DSH RPC（但 adapter 层本来就是干这个的）
- **结论：推荐作为验证路径**，能在 2–3 个迭代内跑出文章 §7.1 那张图

**路径 C：治理层（战略）**
不做 Router，做**所有 Router 都要倚赖的那一层**：权限策略、取证审计、人在环、成本与质量度量。
文章 §8.4 的原文是："如果没有办法很好地解决安全与隐私问题，那么 Super-agent 只有在一个很小且可信的范围才能工作。"——**这是全文唯一一个作者明确说"没解决"的问题**，而它恰好是 mo 已经深耕的领域（决策 broker、卡片指纹校验、超时交回、改动可回退、不自动放行）。
- 需要新写：把 manager kit 从"文案契约"升级为**可调用的策略接口**（任何 Router 都能问：这件事我能不能做 / 该不该问人 / 上次是怎么判的）；把 ledger 从"任务账本"升级为**Agent 行为账本**（谁、在哪个信道、基于什么上下文、做了什么、谁批的）
- 成本：低–中（复用现有 `core/manager/contract.mjs`、`approvals/`、`cli/lib/store.mjs`）
- 收益：不与任何 Router 竞争，也不被任何 Router 替代
- **结论：推荐作为战略**

### 7.3 推荐组合

> **C 为目标，B 为验证。** 先用 B 在一个月内跑出"一个常驻 Router + N 个隔离 Worker + 订阅直通"的最小闭环，用它的真实事件流去反推 C 的策略接口该长什么样；C 的产物（策略接口、行为账本）同时是 B 的安全护栏。

**如果只能做一件事**：把 `core/manager/contract.mjs` 里的 `RULES` 从提示词变成 core 里的可计算不变量（配额、禁止动作、指纹校验），并让所有派单路径（CLI、MCP、未来的 Router）都必须过这一关。这一件事同时提升三条特征的安全性，成本最低。

**明确不要做**：在 mo 里自研 ReAct 运行时与工具循环。重复 DSH 的工作，还会把"跨 Agent 中立"这个唯一护城河填掉。

## 8. 落地路线图

每阶段独立可验收，且都不破坏现有 585 项测试。

### P0 · 事件平面升级（无模型，纯数据结构）
- `core/contract.mjs` 的事件加 `threadId` / `trigger` 语义字段（来源、信道、会话归属）；
- 新增 `core/thread.mjs`：Thread 实体、多对多订阅表、直通路由（纯函数，不碰 IO，符合 core 边界）；
- `hub` 支持按 threadId 聚合查询；`cli/watchdog` 迁到 host 内的定时器（不再依赖 cron）；
- **验收**：同一 thread 的连续事件能命中订阅者；未订阅事件仍进 Router 候选；`npm test` 全绿；`core/` 仍不 import `host/`、`cli/`。
- **风险**：低。不动 ADR。

### P1 · Fast/Slow Path 的 Slow Path（第一次引入模型调用）
- 新增 `core/trigger.mjs`（规则快路径）+ `host/router/filter.mjs`（模型慢路径，走 DSH 或直连）；
- 判定结果只允许三种：`dispatch` / `reply` / `ignore`，全部落在已有 core 契约上；
- 规则层保留"白名单直通"，模型层只做"候选是否值得做"；
- **验收**：给一批脱敏的真实群聊消息，程序层滤掉 90%+ 不误杀；慢路径判定可回放、可审计（每条判定落 ledger）。
- **风险**：中。这是 ADR-0001 的第一次实质让步，**必须先写 ADR-0004 再写代码**。

### P2 · 寄生式 Router（验证双层）
- `host/router/session.mjs`：一个常驻 DSH 会话当 Router，**不配 Bash**（用 profile 限制工具集）；
- Trigger batching 注入；Router 产出结构化动作；
- **验收**：复现文章 §7.1 的对照——同一负载下"单会话 + 提示词委派" vs "寄生 Router"，p95 与 Router 决策数可比；Router token 与决策数落账本。
- **风险**：中高。依赖 DSH RPC 稳定性。

### P3 · Worker 会话化 + 订阅直通
- Worker = `dsh.createSession` + 挂 thread 订阅；回执**双写**（事件 + 文件），去掉文件轮询的阻塞支路；
- Worker 可退订并把事件交回 Router；
- **验收**：同一 PR thread 下两个 Worker 能在不互相通信的情况下发现冲突并自行收敛；派单不再有"等回执"的阻塞窗口。
- **风险**：中。

### P4 · 持久化与治理
- host 无状态化试点（状态外置）+ 端侧 daemon 化（与文章 §5.2 对齐）；
- Watchdog 加"进展/偏航"判断（模型化），并能用自然语言问答；
- manager kit 升级为策略接口 + 行为账本；
- **验收**：桌面 App 关闭后 Agent 仍能响应 Trigger；Watchdog 能识别"Worker 跑了 40 分钟但账本里没有新事实"并介入。
- **风险**：高。安全模型必须同时升级（见 §9）。

## 9. 风险与开放问题

1. **ADR 冲突是首要风险。** ADR-0001 是"观察优先"，P1 之后 mo 就同时是观察者与执行者。必须显式处理成**双模**（默认观察，显式开启托管），否则整个架构的依赖方向与测试边界会一起松动。
2. **mo 的攻击面比文章里的 Super-agent 更大。** mo 有：hook 写权限、本机令牌、钉钉 client_secret、手机推送令牌、语音麦克风。一旦云端 Router 或钉钉入站被提示词注入攻破，攻击者拿到的是**这台开发机的执行入口**。文章 §8.4 承认这一点；mo 因为把"真实环境留在原地"，这个问题只会更尖锐。
3. **钉钉信道目前只承载"决定"，扩到自由文本会立刻引入注入面。** `parseDecision` 的白名单式解析（只认 `A/D + 短码`）是安全设计而不是功能缺失——扩的时候必须保留"自由文本永不直接执行"的边界。
4. **批处理的失效模式**（§4.2）：一旦某些 Trigger 需要 Router 更长思考，合并就从收益变成"一次判断错一批"。需要按 Trigger 类型分桶批处理，而不是全局合并。
5. **长程记忆没有解。** 文章 §8.1 自己承认引用图只解决"近期"。mo 的 ledger 是 JSONL 事实流，其实是更好的长期记忆底座（append-only、可审计），但也需要分层与压缩策略。
6. **Worker 间冲突靠"机会性发现"。** 无锁、无仲裁。真实场景里两个 Worker 改同一文件、或对同一 PR 反复打转时，需要显式的协调协议或 Worker 级互斥。
7. **许可证**：mo 是 PolyForm Noncommercial，不是 OSI 开源。任何"带云端计算面"的形态都需要先想清商业授权（见 [COMMERCIAL.md](../../COMMERCIAL.md)）。
