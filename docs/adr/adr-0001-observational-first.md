# ADR-0001：观察优先，暂不做 ACP 托管

状态：**已采纳**　日期：2026-10-16

## 背景

我们希望手机能看 Agent 状态、并在关键卡点远程批准。ACP 提供了一条标准路径：由我们启动 Agent 子进程，接管它的 stdin/stdout，于是 `session/request_permission` 会发给我们，我们就能转发到手机。

但 ACP 是「客户端启动 Agent」模型，意味着：
- Agent 原本的终端 TUI 由我们取代 —— **用户必须改到我们的 App 里干活**；
- 会话生命周期、认证、崩溃恢复都由我们负责；
- 用户终端里原本那个会话与我们托管的会话是两套，互不相干。

## 决策

**暂不做 ACP 托管。** 走「观察优先 + hook 卡点介入」路线。

理由：核心价值是「不打扰你原来的工作方式，只在卡点上叫你一声」，而 ACP 托管要求用户迁移工作界面，与这个价值主张冲突。

## 结果：能力边界

| 通道 | 作用 | 覆盖 |
|---|---|---|
| 进程发现 + 日志 tail | 看状态（在跑/在等/完成/失败） | 全部 CLI Agent |
| Hook（放行型） | **远程批准** | Claude Code、Cursor、Gemini、Qwen、Copilot(带 bug)、Qoder |
| Hook（仅拦截型） | 只能远程**拒绝** | Codex |
| Hook（仅通知型） | 只能提醒 | 其它 |
| tmux send-keys | 通用兜底批准（粗糙） | 任何在 tmux 里跑的 Agent |

**必须接受的损失**：
1. **Codex 不能远程批准**，只能看 + 远程拒绝。
2. 没有放行型 hook 的 Agent 是**只读**的。
3. 失去了「一套客户端吃一片生态」的效率，改为**每家一个 profile**，长尾维护成本落在我们身上。

## 保留的扩展点

- `dsh.mjs` 里已有的会话/事件抽象保留；
- 适配层预留 `acp` adapter 槽位，**只留接口不实现**；
- 将来若出现「用户愿意由我们托管」的场景（例如无 UI 的服务器、或自动化任务），可低成本补上。

## 关键设计约束（由本决策加强）

因为**用户的终端就是降级后的界面**，hook 在失败时必须：

```
手机不可达 / mo-agent未运行 / 超时
        ↓
不做决策，退出码 0，交回本地终端
        ↓
用户在原来的终端里照常看到提示
```

绝不能 fail-open（等于绕过安全确认），也不宜 fail-closed（会把 Agent 卡死）。

## 被否决的替代方案

- **ACP 托管为主**：能力最全、协议最标准，但改变用户习惯，产品代价过大。
- **只做观察，不做批准**：实现最简单，但失去最有价值的场景（远程放行），产品没有存在理由。
